# 개인화 당류 판정 기능 — 기획 문서

- 작성일: 2026-08-19 (개정 2026-08-20: 판정 엔진 점검 반영)
- 상태: 설계 확정 (구현 계획 수립 전)
- 배경: 팀 리더의 IR 데모("건강식이라 믿었던 것들") 요청 + 개인화/맞춤화 방향성

## 1. 목적

바코드/사진 하나로 제품을 스캔했을 때, **"이 당류가 나한테 많은가?"** 를
사용자 개인 기준으로 즉시 판정해서 보여준다. 하루 누적이 아니라
**제품 1개 vs 한 끼 한도**의 즉석 비교다.

이번 작업은 데모용 최소 기능이 아니라, 이후 개인화(다른 영양소 기준,
목표 관리 등)를 얹을 수 있는 **개인화 프로필의 첫 삽**으로 설계한다.
단, 이번 범위에서 다루는 영양소는 당류(+위험 당알코올 환산)뿐이다.

## 2. 범위

### 포함
1. 개인화 프로필(`SugarProfile`) — 로컬 저장, 확장 가능 구조
2. 당류 개인 판정 함수 — 공용 파일 1개, 순수 함수
3. 결과 화면 플로우 — 배너 → 온보딩 시트 → 히어로 교체, 양 슬라이더 실시간 연동
4. 스캔 개선 — 전면 1장 빠른 매칭 (DB 등록 제품)
5. 마이페이지 프로필 수정 진입점

### 제외 (Non-goals)
- 하루 누적 당류 추적 (product_logs 스키마 확장 없음)
- 당류 외 영양소의 개인 기준
- 서버 프로필 동기화 (Supabase 테이블·컬럼 신설 없음)
- 바코드 스캔 재활성화 (FeatureFlags.barcodeScan은 false 유지)
- 앱 첫 실행 온보딩 화면 (질문은 결과 화면 이후에만 등장)

## 3. 개인화 프로필

### 데이터 모델
```dart
class SugarProfile {
  final SugarGoal goal;      // bloodSugar | weight | general
  final double? weightKg;    // null 허용 (기본 2000kcal 가정)
  final int? mealsPerDay;    // null 허용 (기본 3)
}
```

### 저장
- SharedPreferences에 JSON 1키 (`sugar_profile`). 선례: `lib/core/location_cache.dart`
- Supabase 변경 없음. 서버 동기화가 필요해지는 시점에 마이그레이션 검토
- 신규 파일: `lib/core/sugar_profile.dart` (모델 + load/save)

### 온보딩 질문 (총 3입력, 바텀시트 1장)
팀 리더의 Q1(이유)·Q2(엄격도)는 사실상 같은 축이므로 **1문항으로 통합**한다.
통합 선택지가 산식의 비율에 직접 매핑되므로 별도 계수가 필요 없다.

| 통합 질문: "당, 얼마나 조심해야 할까요?" | 열량 대비 유리당 비율 |
|---|---|
| 🩸 혈당 관리 중이에요 | 5% |
| ⚖️ 체중 관리 중이에요 | 7.5% |
| 🌿 그냥 건강하게 먹고 싶어요 | 10% |

- 체중(kg), 하루 식사 횟수: 선택 입력 (스킵 가능, 스킵 시 기본값)
- 데모는 통합 질문 1개만 답해도 성립

## 4. 판정 함수 (공용 파일 1개)

- 신규 파일: `lib/core/sugar_judge.dart`
- 기존 `rulebook.dart`와 동일 철학: **런타임 계산만, DB 저장 없음**

### 산식 (WHO 유리당 권고 기반)
```
하루 열량   = clamp(weightKg × 30, 1400, 2400) kcal   (weightKg 없으면 2000)
하루 한도 g = 하루 열량 × goal 비율 ÷ 4
한 끼 한도 g = round(하루 한도 ÷ mealsPerDay)          (없으면 3끼, 정수 반올림)

유효당류 g  = 당류 + 0.5 × 위험 당알코올               (아래 참조)
비율        = 유효당류 ÷ 한 끼 한도
```

- **열량 클램프(1,400~2,400)**: `체중×30`을 그대로 쓰면 체중이 클수록 한도가
  커져 "체중 관리" 목표와 정반대로 움직인다. 상하한으로 역설을 차단한다.
  구간은 홍범(의학 배경) 최종 확정.
- **한 끼 한도는 정수 g로 반올림**: "8.75g"은 가짜 정밀도. 추정치임을
  감안해 정수로 보여주는 것이 더 정직하고 읽기 쉽다.

예시 (70kg·3끼): 혈당 9g / 체중 13g / 건강 18g
예시 (미입력, 2000kcal·3끼): 혈당 8g / 체중 13g / 건강 17g

### 위험 당알코올 환산 (rulebook 재사용)
- 룰북의 `riskySugarAlcohol` 세트(말티톨·자일리톨·소르비톨·폴리글리시톨,
  `rulebook.dart:35`)를 그대로 재사용한다. **혈당을 올리는 당알코올만 ×0.5 환산**하고,
  에리스리톨·알룰로스 등 혈당영향 0인 감미료는 환산하지 않는다.
- 일괄 환산 금지 사유: 에리스리톨 기반의 착한 제로 제품까지 🔴로 판정하면
  "좋은 감미료 vs 함정"을 구분하는 앱의 존재 이유와 충돌한다.
- 적용 규칙: 제품 감미료 slug 중 risky 세트에 포함된 것이 있을 때만
  당알코올 총량에 0.5를 곱해 가산 (룰북 당알코올 함정과 동일한 감지 조건).
  감미료별 개별 g(`ProductSweetener.amountG`)이 있으면 risky 성분 합계만 사용.
- 환산 계수 0.5의 근거: 말티톨 GI ≈ 35 (설탕의 약 절반). 계수 확정은 홍범.

### 판정 (팀 리더 기준 그대로)
| 비율 | 판정 |
|---|---|
| ≤ 0.5 | 🟢 괜찮음 |
| 0.5 초과 ~ 1.0 | 🟡 주의 |
| 1.0 초과 | 🔴 피하세요 |
| 당류 미확인 | ⚪ 판정 불가 (기존 혈당 히어로 유지) |

### "당류 미확인" 감지 (구현 필수 선행)
`Product.sugar`가 non-null `double`이라 현재 구조로는 **OCR 미표기와 진짜 0g이
둘 다 0으로 들어와** 미표기 제품이 🟢로 오판된다. 해결:
- OCR 응답(파서)에서 당류 미확인 여부를 별도 플래그로 내려 임시 Product에만
  전달한다 (모델 nullable화 대비 파급 최소 — 권장).
- 이 플래그가 참이면 판정 함수는 무조건 ⚪ 판정 불가를 반환.

### 시그니처
```dart
SugarVerdict judgeSugar({
  required double? sugarG,          // 1회 제공량 기준. null = 미확인 → ⚪
  required double sugarAlcoholG,
  required List<String> sweetenerSlugs,  // risky 여부 판별용
  required SugarProfile profile,
});
// SugarVerdict: { level(ok|watch|avoid|unknown), ratio, mealLimitG, effectiveSugarG }
// 양 배수(portion) 반영은 호출부 책임: 배수를 곱한 g을 넘긴다 (함수는 순수 유지).
```

- 테스트: `test/sugar_judge_test.dart` — 경계값(0.5, 1.0), null 당류(⚪),
  체중 클램프 상·하한, 미입력 기본값, risky/non-risky 당알코올 분기
  (말티톨 → 환산, 에리스리톨 → 미환산)

## 5. 결과 화면 플로우

### 상태별 히어로 (VerdictHero)
| 상태 | 표시 |
|---|---|
| 프로필 미설정 | 기존 혈당 히어로 유지 + 하단 배너 "이게 나한테 많은 걸까요? →" |
| 프로필 설정됨 | **개인 당류 판정이 메인 신호등으로 교체.** 기존 혈당 등급은 보조 칩/한 줄로 강등 |
| 당류 미확인 | 기존 혈당 히어로 유지 + "당류 정보 없음" 표시 |

- 판정 등급과 무관하게 **기존 함정 불릿(traps)·zeroBusted 스트립은 히어로에 유지**한다.
  "제로 표기지만 말티톨 ○g" 스토리가 여기서 나온다.

### 판정 배지 표현 ("복잡하지 않은 전문성")
- 배지 아래 **게이지 바 1개**: "내 한 끼 한도 13g 중 18g (138%)" — 숫자 나열
  대신 시각 은유 하나로.
- 게이지 아래 작은 근거 라벨: **"WHO 권고 × 내 프로필 기준"** — 탭하면
  산식 설명 바텀시트 (전문성의 출처를 한 줄로, 원하는 사람만 깊이).
- **양 조절 슬라이더(`portion_slider`) 실시간 연동**: 슬라이더를 움직이면
  게이지·배지가 즉시 재판정된다 ("반 개만 먹으면 🟡"). 기존 위젯 재사용.

### 온보딩 시트 (데모 동선)
1. 결과 화면 배너 탭 → 바텀시트: 통합 질문 1개 (+ 선택: 체중, 식사 횟수)
2. 응답 완료 → 시트 닫힘 → **같은 결과 화면의 히어로가 즉시 개인 판정으로 교체**
   (데모의 하이라이트 순간 — 화면 이동 없이 in-place 변신)
3. 이후 모든 스캔에 판정 자동 적용

### 진입점
- 마이페이지(`account_screen.dart`)에 "내 당류 기준" 행 추가 → 같은 바텀시트 재사용

## 6. 스캔 개선 — 전면 1장 빠른 매칭

현재: 3장(전체샷/원재료/영양성분표) 필수 → `submit-product` 1콜.

변경: 전면샷 촬영 직후 매칭을 먼저 시도한다.
- 엣지 함수의 기존 전면사진 매칭 로직(`recognizeWithClova` → 등록제품/가격카탈로그)을
  1장 입력으로 호출하는 경량 경로 추가 (신규 함수 또는 `submit-product`에 mode 파라미터 — 구현 시 결정)
- 매칭 성공 → 나머지 2장 생략, DB 제품으로 즉시 `ResultScreen`
- 매칭 실패 → 현행 3장 플로우로 자연스럽게 계속
- 터치 파일: `capture_screen.dart`, `capture_controller.dart`, `ocr_service.dart`,
  `supabase/functions/submit-product/` (또는 신규 함수)

데모 제품을 사전 등록해두면 사진 1장 → 수 초 내 결과가 가능하다.

## 7. 데모 시나리오 (30초)

제품: **롯데 제로 초코파이** — "제로" 표기 but 말티톨 다량, 순탄수 높음.
실물 영양성분표 수치로 사전 등록·검증한다.

1. 앱 실행 → 홈에서 바로 스캔 진입 (기존 구조 그대로, 질문 없음)
2. 전면 1장 촬영 → 빠른 매칭 → 결과 화면 (사전 등록 덕에 즉시)
3. 히어로: "제로인데?" → zeroBusted 스트립 + 당알코올 수치 노출
4. 배너 "이게 나한테 많은 걸까요?" 탭 → 질문 응답
5. 히어로가 개인 판정으로 교체: 🔴 피하세요 (말티톨 환산 기준) + 게이지 바
6. (여유 시) 양 슬라이더를 반으로 → 🟡로 실시간 변화 / 먹은 기록 → 다이어리

백업 녹화 30초: 위 동선 그대로. 현장 와이파이 리스크 대비.

## 9. 구현 순서

1. **프로필 + 판정 함수** (`sugar_profile.dart`, `sugar_judge.dart`, 테스트)
   — 당류 미확인 플래그 경로(OCR 응답 → 임시 Product) 포함. UI 없이 완결
2. **결과 화면** — 배너, 온보딩 바텀시트, 히어로 교체, 게이지·근거 라벨,
   양 슬라이더 연동, 마이페이지 진입점
3. **1장 빠른 매칭** — 클라이언트 + 엣지 함수 (독립 작업, 실패해도 ①②로 데모 성립)
4. **데모 준비** — 제품 등록, 리허설, 녹화

각 단계는 독립적으로 main에 머지 가능하다 (브랜치 워크플로: main 단일화).
